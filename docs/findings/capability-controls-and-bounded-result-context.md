# Scalable capability controls and bounded numerical result context

Status: initial target implementation, Stages 7.0.1 and 7.1; live evaluation pending.

## Capability controls
User feedback: adding a visible checkbox for each source creates friction and visual clutter; an explicitly attached file should not also require a checkbox. Prefer one discoverable, persistent capabilities menu, with deliberate attachments represented directly and removable. Keep descriptions aligned with the actual enabled state. Default enabled read-only capabilities do not authorize transmission, solver execution or modifications. Explicit request preview/approval remains independent. Persist preferences locally, not credentials or attachments. Handle malformed preferences conservatively. On revocation exclude affected earlier conversation from future requests; an old transcript must not act as a hidden alternative source. The initial implementation includes all enabled bounded read-only sources, with question-specific knowledge selection; general relevance routing is not yet implemented.

## Numerical datasets
Bind retained results to immutable numerical inputs and the actual cache identity. Separate the latest attempt, displayed subset, retained cache and underlying operation provenance. Reused modes may originate from different attempts; do not reattribute them to a new solve. Compare freshness deterministically with meaningful numerical identity; plot-only controls and mode selection may have different semantics. Report missing requested modes separately.
Provide exact aggregate statistics across the full grid of each included mode, bounded representative points and targeted retrieval of actual grid values. Label scope, omissions and sampling; do not infer unobserved continuous trends, interpolate or extrapolate without explicit qualification. A finite complex solution is not necessarily a validated guided mode, and missing, skipped, uncertain or lost points do not prove physical cutoff. Distinguish stored numerical diagnostics from plot-specific annotations. Keep full source arrays unchanged, use existing application operations, and avoid introducing another solver. Record provenance/metadata in normal opt-in diagnostics and exact approved messages only in detailed diagnostics.

No numerical solver algorithm changes. Scope does not include non-frequency sweeps, arbitrary plot inspection or historical result comparison. No target code, research data or transcripts in framework. Generalize these patterns only after testing another application.


## Stage 7.1.1 — session-scoped submission and credential UX
User feedback favored a single submission warning after launch and a manual key command rather than a persistent toggle. One observed live request was cancelled during key entry, followed by nine successful requests. The local assistant now obtains explicit session consent on the first request; future deliberate Ask/Enter submissions to the same approved provider use enabled context, including changed settings, results, attachments and eligible conversation history. Make this scope clear at consent, keep the provider visible, allow reset and per-request review, and never persist consent across launches. Capability preferences and execution authorization remain independent; session consent does not authorize background activity, new providers, or future actions. Manual credentials are masked, held in memory for the run, and separate from persisted capability settings and debug logs. Reuse existing secure credential storage without altering it. Record preparation, actual review, session consent and deliberate submission separately rather than implying a warning was shown every time. This is a user-selected UX tradeoff, not a general default recommendation for sensitive applications.
