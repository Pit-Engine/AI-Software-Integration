# First controlled computation: execution is separate from changing working state

Status: first-target Stage 8.1 local prototype; offline adapter/GUI validation and a reconstructed scientific diagnostic completed. Live model-directed execution pending.

## Reusable design pattern
Start with a narrowly typed, detachable computation on immutable inputs using the application's existing numerical backend, rather than allowing an agent to edit the live working document or invoke arbitrary code. Separate the permission to read, propose, execute a temporary job, persist evidence, and commit changes to the working configuration. A one-shot arming control exposes an execution tool for one request; it is not approval to launch. Validate typed arguments, units, quantities, allowed operations, estimated size and resource ceilings before presenting the actual plan. Show originating parameters and numerical settings, computed grid, output/retention behavior and cancellation semantics. Require an application-owned approval of this plan, not ambiguous prose or a model's assertion that consent was granted. Keep read-only capabilities and public search authorization independent.

Use the original backend, fresh per-job objects, isolated result identity and actual progress callbacks. Record an operation ID before launch, terminal outcome, completeness counts and evidence lineage. Distinguish successful protocol transport, a terminal job, a returned result, a finite root and a scientifically validated result. A failed or cancelled calculation can have partial data. Do not automatically rerun on ambiguous execution outcome or let read-only cache/loop detection double-submit a computation. One approved attempt may exhaust a separate job budget even when many inexpensive read-only calls remain. Before increasing autonomy, test in-flight cancellation, partial outputs, archive failures, retention, user rejection, and preservation of working state. Cooperative cancellation is not hard process termination; already committed writes cannot be recalled. A later persistent job scheduler will need a durable execution ledger, idempotency, separate per-job and cumulative compute budgets, and explicit resume policy.

Expose newly computed results by opaque IDs through the same validated evidence retrieval interfaces used for existing results. A request-local result and persistent archive record have different lifetimes; if archived, include operation provenance and outcome, use approved existing retention and checksum guards, and invalidate conversation evidence when the record is revoked. No implicit changes to live display or user files. Prefer deterministic diagnostics with explicit definitions and units. Independently validate a diagnostic formula against a different numerical integration or analytic reference, distinguish formula accuracy from underlying model accuracy, and keep case-specific geometry, raw results, scripts and logs in the target.

## First-target evidence
The initial adapter exposes one per-job approved detached computation per explicitly armed Ask, with finite grid/mode/iteration limits, cooperative time budget and optional selected-coordinate diagnostic. It retains the original backend and working GUI inputs/results; no general setting mutation, open-boundary jobs, fitting, arbitrary execution, auto-restart or multi-job approval. Capture uses existing opt-in archive and distinct record identifiers. 147 AI unit tests passed, including six new execution tests (real analytic-reference computation, mocked native exchange, argument validation, rejection, partial outcome, archive and diagnostic evidence). Four focused execution GUI tests passed cleanly, including actual computation, same-turn result retrieval, no working-state mutation, rejection/expiry, archival and revocation, and in-flight Stop with a mocked long calculation. A combined regression runner reported 44 tests OK before command timeout at teardown; not a clean process-exit claim. Original numerical modules unchanged. Independent reconstruction of a user-reported ambiguous scientific case confirmed an arithmetic diagnostic using a different integration technique; it supports a physical hypothesis but does not independently prove branch identity or general solver validity. First target retains the script and results locally. No live provider-driven execution, Windows test or full numerical regression yet.
